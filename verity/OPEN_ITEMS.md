# VERITY — Open Items / Production-Readiness Register

Honest status as of this review. Verity is a **working application**
(Phases 1–3 of an 8-phase build, plus four items pulled forward from
later phases — CSV import from Phase 4, certification campaigns from
Phase 5, remediation task tracking and access requests/approval workflow
from Phase 6, which is now fully done ahead of its gate) — the Enterprise
Dashboard, Identity Directory, Access Inventory/Unmatched Accounts (manual
correlation plus deterministic match suggestions), Application Catalog +
connector catalog (with a real CSV import sync engine), Enterprise Access
Matrix, Dynamic Fields, self-service account/password management, a full
admin user-management flow (create with password, edit details, reset
password, activate/disable) inside the Admin IAM console,
Settings/Branding, Audit trail, certification campaigns (scope frozen at
launch, manager- or fixed-reviewer assignment, audited approve/revoke
decisions), remediation task tracking (auto-opened from a campaign
revoke, or flagged manually), and access requests (request an entitlement
for an existing account, approved by the application's system owner or
an admin, which genuinely creates the resulting grant) are built and
exercised by an automated test suite (190 assertions, all passing).
Everything below is grouped by theme,
each with **Impact** and **Suggested action**. Nothing in this list should
be read as "broken" — it is "not yet built," stated plainly rather than
implied to exist.

## Security Hardening

| Item | Impact | Suggested action |
|---|---|---|
| ~~No MFA~~ — **resolved (TOTP; WebAuthn still not implemented)** | `app/Support/Totp.php` + `app/Support/Mfa.php`: self-service TOTP enrollment from "My Account," confirmed only after a real current code (never activates on an unproven secret), 10 single-use bcrypt-hashed recovery codes shown once. Login with MFA enrolled is two-step — a correct password alone sets a narrowly-scoped, 5-minute pending-challenge session state (a different session key from the one `Auth::user()` actually reads, so it grants no authenticated capability by construction), and code/recovery-code attempts are rate-limited the same way password attempts are. An admin can reset a locked-out user's MFA (`iam.manage`). Hand-rolled (zero Composer dependencies, this app's standing constraint) but verified directly against RFC 4226 Appendix D's and RFC 4648 §10's own published test vectors in `tests/unit_test.php`, not just trusted on inspection — unlike the JWT/OIDC case noted below, TOTP's algorithm is small and fully specified enough to test against the spec's answer key directly. Found and fixed two real, unrelated bugs while building this. First: `Session::regenerate()` had the exact same missing-guard defect `Session::destroy()` was fixed for earlier — `session_regenerate_id()` called unconditionally, warning under CLI SAPI where no real session is ever started; the MFA challenge's own session-fixation defense was the first code path to newly reach it. Second, a genuine test-isolation bug, not a production one: an early version of the regression tests called a *successful* `Auth::completeMfaChallenge()` directly inside the shared test process, which ends in `establishForUser()` — caching `Auth::$requestUser` for the rest of that process (the same private static `Auth::user()`'s own doc comment warns about). That stale cache then leaked into a later, unrelated, already-existing test (`Users::setStatus()` in the `Auth::user()` live-revalidation group), which relies on `Audit::log()`'s implicit actor-id fallback — producing a real foreign-key violation on a since-rolled-back user id. `Audit::log()`'s own `try/catch` caught it (so no assertion ever failed, and no production code path is affected — every real request is a fresh PHP process with no cross-request cache to leak), but that unrelated test's audit row silently never got written. Fixed by moving the one assertion that actually needs a successful challenge into its own subprocess, exactly matching this file's own established pattern for testing anything touching `Auth::$requestUser` — confirmed fixed by running the full suite multiple times afterward, not just once. Verified live end-to-end in a browser: enrolled a real account, confirmed with a real generated code, received recovery codes, logged out, logged back in and was correctly challenged for a second factor, completed it with both a TOTP code and (on a separate account) a recovery code, confirmed a used recovery code could not be reused, and confirmed the admin reset path. Regression-tested (31 new logic-only assertions for the RFC vectors + drift-window boundaries, plus DB-backed and subprocess-isolated assertions for the full enrollment/challenge/throttle/disable lifecycle) | None for TOTP — already shipped. WebAuthn/hardware security keys are not implemented — TOTP alone was judged sufficient for this build; add WebAuthn only if a concrete requirement for it shows up, not speculatively |
| ~~No account lockout / login rate limiting~~ — **resolved** | `Auth::isLoginThrottled()` enforces both a per-account limit (10 failures / 15 minutes, against one email regardless of source IP) and a broader per-IP limit (30 failures / 15 minutes, across any emails from one source — catches a credential-stuffing spray). Both are soft, time-boxed lockouts that expire on their own, not permanent — a hard per-account lock with no expiry would let an attacker lock out a legitimate user just by guessing their password wrong repeatedly. Reuses the existing `audit_event` log rather than a new table; two new composite indexes (`idx_audit_action_target_created`, `idx_audit_action_ip_created`) keep the per-request check fast as that table grows.
